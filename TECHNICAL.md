# Technical architecture

## Scope and design

The core engine is the source of truth. REST endpoints and MCP tools invoke it directly; the browser consumes a static JSON snapshot generated by `python -m inventory.build_demo`. The committed snapshot is checked against the engine by CI. A static page is deliberately independent of live services and requires no keys.

```text
Synthetic records + fictional SOPs
                |
           Python core
         /       |       \
    REST API   MCP tools   JSON export -> static dashboard
                                  |
                           Optional browser worker AI
```

The dashboard reads its own origin by default; an opt-in browser worker downloads public model/runtime assets. Text is rendered with DOM text nodes, not HTML injection. Reports are generated in Python and downloaded as Markdown; JavaScript does not recalculate financial totals. The export contains no time-dependent fields and is reproducible in content.

## Metric definitions

| Metric | Definition |
| --- | --- |
| Quantity variance | Physical count minus system quantity |
| Value variance | Signed quantity variance multiplied by unit cost (GBP) |
| Absolute value variance | Sum of absolute signed value variances |
| Exact SKU match rate | Number of records with zero variance divided by counted records, as a percentage |
| Discrepancies | Number of records with non-zero variance |

The match rate is SKU-based, not a unit-weighted inventory accuracy measure. Filters do not change the aggregate dashboard metrics. The six-record fixture contains four discrepancies, 489 system units, 479 physical units, a net variance of -10 units, an absolute variance of 18 units and an absolute value variance of £406.50.

## Investigation workflow

1. Identify the SKU and location; inspect physical and system counts.
2. Separate observed sample evidence from possible explanations.
3. Consult relevant fictional procedures for recount and reconciliation.
4. Escalate unresolved differences; an authorised human must approve any adjustment.
5. Export an investigation report retaining evidence and the unverified conclusion.

Example: SKU-101 has a shortage of four units (£34.00 signed negative variance). A recent transfer is recorded in the fixture; an unreconciled transfer is a possible explanation, not a confirmed root cause.

## Boundaries and security

No real warehouse, SAP or employer information is used. No write endpoints or stock-adjustment tools are exposed. Local services are intended for loopback use, not public deployment. There is no commercial AI adapter or API key configuration. Optional browser AI uses the selected synthetic investigation and associated fictional SOPs locally. The model selects a permitted investigation focus; an independent validator maps the choice to canonical data and SOP text. Selection is advisory and requires human verification.

This is a demonstration, not a secure multi-user service. See [SECURITY.md](SECURITY.md) for the implemented controls and limitations. Authentication, authorisation, rate limiting, comprehensive security auditing, hash-locked cross-platform builds, broader model quality evaluation, accessibility auditing and cross-browser testing are not yet complete. API tests use HTTPX ASGI transport rather than the deprecated Starlette TestClient.

## Test strategy

Python regression tests cover the backend, deterministic explanation and actual MCP stdio client/server communication. Export tests check every record, case, SOP and report against Python. Chromium tests serve the static site over loopback HTTP and verify filtering, selection, report download, mobile layout, fetch failure handling, browser AI consent and fallback. A six-case real-model test exercises public asset loading and local inference and records validated selections and canonical explanations for human review. The release CI also checks reachable Git history and selected upstream asset integrity. See [AI.md](AI.md).

## Deployment

GitHub Pages is configured for deployment from `main` and the `docs/` directory after release acceptance. Relative paths and `.nojekyll` support static hosting. No custom deployment workflow or live API hosting is required. GitHub Pages availability depends on repository visibility and account plan.
